\chapter{Informacje wstępne}
\section{Cel i zakres pracy}
Celem pracy jest zaprojektowanie oraz implementacja systemu \textbf{RacePortal} --- platformy internetowej (z~uzupełnieniem mobilnym) służącej jako centralny katalog wydarzeń motorsportowych w~Polsce oraz narzędzie do obsługi zapisów kierowców.

Zakres obejmuje:
\begin{itemize}
  \item aplikację webową (katalog, konta, garaż, zgłoszenia, panele organizatora i~administratora);
  \item API REST z~trwałą bazą danych wydarzeń, użytkowników i~zgłoszeń;
  \item powiadomienia e-mail (potwierdzenia, statusy, weryfikacja konta);
  \item mapę wydarzeń oraz wyznaczanie trasy dojazdu (OSRM; opcjonalnie Google Maps przy kluczu API);
  \item aplikację mobilną Expo jako \emph{wizytówkę} katalogu z~CTA zapisu na stronie webowej;
  \item konteneryzację (Docker Compose) oraz podstawowy zestaw testów automatycznych.
\end{itemize}

Poza zakresem MVP pozostają m.in.\ natywne płatności online, pełny upload plików binarnych, push notifications oraz publikacja aplikacji mobilnej w~sklepach.

\section{Wizja rozwiązania}
\label{sec:wizja}
RacePortal ma być \textbf{jednym miejscem} odkrywania i~obsługi startów motorsportowych w~Polsce: kierowca znajduje wydarzenie, sprawdza wymagania względem własnego garażu i~składa zgłoszenie; organizator publikuje imprezę i~zarządza listą uczestników; administrator moderuje treści i~role.

Wizja produktowa zakłada:
\begin{itemize}
  \item publiczny katalog z~trzema widokami (lista, mapa, kalendarz) na wspólnych filtrach;
  \item ujednolicony proces zapisu ze statusami i~powiadomieniami e-mail;
  \item wyraźny podział ról \texttt{USER} / \texttt{ORGANIZER} / \texttt{ADMIN} (gość przegląda bez konta);
  \item mobilną ścieżkę discovery (Expo) z~konwersją zapisu na web;
  \item uruchamialne środowisko demonstracyjne (Docker) oraz wdrożenie produkcyjne za Cloudflare Tunnel.
\end{itemize}

Szczegóły warstw technicznych (web React/Vite, API Spring Boot, MySQL, mobile Expo, \texttt{packages/api-types}) opisano w~rozdziale~\ref{ch:projekt} oraz w~rozdziałach implementacyjnych. Kod źródłowy utrzymywany jest w~repozytorium projektu~\cite{raceportal:repo}.

\section{Struktura pracy}
Kolejne rozdziały obejmują: słownik pojęć, opis problemu dziedzinowego, kontekst biznesowy (w~tym karty udziałowców), analizę SWOT, planowanie projektu, analizę wymagań (w~tym karty wymagań i~diagramy UML), projekt systemu (m.in.\ Figma, diagram klas), opis realizacji oraz szczegóły implementacji backendu, frontendu i~mobile, bezpieczeństwo, testowanie, prezentację systemu, nakład pracy, \textbf{wkład własny} oraz podsumowanie (z~uwzględnieniem ograniczeń wydajnościowych RPS).

\chapter{Słownik pojęć}
\begin{description}
  \item[Wydarzenie (event)] Zorganizowany start / impreza motorsportowa (np.\ track day, drift, rally), opisana datą, lokalizacją, kategorią i~wymaganiami.
  \item[Katalog] Publiczny wykaz wydarzeń z~widokami lista, mapa i~kalendarz oraz filtrami.
  \item[Garaż] Zbiór pojazdów przypisanych do konta kierowcy, wykorzystywanych przy zapisie na wydarzenie.
  \item[Zgłoszenie (registration)] Wniosek o~udział w~wydarzeniu, posiadający status (np.\ PENDING, APPROVED, CANCELED).
  \item[carMatch] Mechanizm dopasowania kategorii/klasy pojazdu do kategorii wydarzenia (aliasy nazw).
  \item[Organizator] Użytkownik z~rolą ORGANIZER, uprawniony do tworzenia i~zarządzania własnymi wydarzeniami oraz zgłoszeniami.
  \item[Administrator] Użytkownik z~rolą ADMIN, moderujący wydarzenia, wnioski o~rolę organizatora i~role kont.
  \item[Wizytówka mobilna] Wersja aplikacji Expo ograniczona do przeglądania katalogu; zapis odbywa się na webie (CTA).
  \item[JWT] JSON Web Token --- token sesji używany do uwierzytelniania żądań API.
  \item[RBAC] Role-Based Access Control --- kontrola dostępu oparta o~role.
  \item[OSRM] Open Source Routing Machine --- publiczny serwis wyznaczania trasy wykorzystany jako domyślny provider.
  \item[MVP] Minimum Viable Product --- minimalny zakres funkcji przyjęty do odbioru projektu.
  \item[RPS] Requests Per Second --- metryka obciążenia (np.\ docelowy test 50~RPS przy 10k rekordach).
\end{description}

\chapter{Opis problemu}
\section{Charakterystyka rynku wydarzeń motorsportowych}
% TODO: rozwinąć na podstawie pitch / research
Amatorski i~półprofesjonalny motorsport w~Polsce obejmuje liczne formy aktywności (track day, drift, rally, wyścigi górskie itp.). Informacje o~terminach i~zapisach są często rozproszone pomiędzy strony organizatorów, media społecznościowe oraz komunikatory.

\section{Problemy związane z~organizacją wydarzeń i~zapisami uczestników}
Organizatorzy potrzebują narzędzia do publikacji wydarzenia, zbierania zgłoszeń, weryfikacji wymagań wobec pojazdu/kierowcy oraz komunikacji statusu zgłoszenia. Ręczne procesy (arkusze, wiadomości prywatne) są podatne na błędy i~trudne do skalowania.

\section{Problemy informacyjne po stronie kierowców i~organizatorów}
Kierowcy mają trudność ze znalezieniem aktualnych startów w~jednym miejscu, porównaniem wymagań wydarzenia z~posiadanym pojazdem oraz śledzeniem statusu zapisu. Organizatorzy --- z~utrzymaniem spójnej listy uczestników i~powiadomień.

\section{Uzasadnienie potrzeby stworzenia systemu RacePortal}
RacePortal odpowiada na potrzebę \textbf{centralnego katalogu} oraz \textbf{ujednoliconego procesu zapisu} z~rolami użytkowników, przy zachowaniu prostego uruchomienia demonstracyjnego (Docker) i~ścieżki mobilnej (odkrywanie wydarzeń).

\section{Aspekty techniczne i~organizacyjne problemu}
Wyzwania obejmują: spójny model danych wydarzeń i~zgłoszeń, bezpieczeństwo kont (JWT, RBAC), walidację wymagań wydarzenia względem garażu, integrację mapy/trasy, dostarczalność maili w~środowisku deweloperskim oraz świadomy podział odpowiedzialności web vs mobile.

\chapter{Kontekst biznesowy}
\label{ch:biznes}
Niniejszy rozdział sytuuje RacePortal w~kontekście produktowym i~organizacyjnym: identyfikuje segmenty odbiorców, udziałowców oraz propozycję wartości, a~następnie opisuje kanały dystrybucji, zasoby i~działania kluczowe, model funkcjonowania platformy, realność wdrożenia oraz uwarunkowania prawno-etyczne. Punktem wyjścia są założenia Dokumentu Założeń Wstępnych (DZW), karty projektu, Business Model Canvas (BMC / materiały KMR) oraz scenariusze walidacji wywiadami, konfrontowane z~faktyczną implementacją systemu (role RBAC, katalog wydarzeń, garaż, zgłoszenia, maile, wdrożenie produkcyjne).

Należy zaznaczyć, że segmentacja w~materiałach KMR została sformułowana jako \emph{założenie koncepcyjne}, a~nie jako wynik reprezentatywnych badań rynkowych. Dokument \emph{Interview Validation} definiuje hipotezy, skrypt wywiadu oraz metryki sukcesu; nie zawiera wyników przeprowadzonych wywiadów, dlatego w~dalszej części nie są one przytaczane jako dane empiryczne.

\section{Segmentacja użytkowników}
\label{sec:segmentacja}
Z~punktu widzenia produktu wyróżnia się cztery podstawowe segmenty korzystające z~systemu, odpowiadające poziomom dostępu zaimplementowanym w~warstwie aplikacji. Segmentacja ta jest spójna z~DZW (kategorie użytkowników MVP), z~BMC (kierowcy, pasjonaci/kibice, organizatorzy) oraz z~modelem bezpieczeństwa opartym o~role.

\textbf{Gość (użytkownik anonimowy)} korzysta z~publicznego katalogu bez uwierzytelnienia. W~implementacji nie istnieje osobna rola \texttt{GUEST} --- dostęp gościa wynika z~konfiguracji publicznych ścieżek API (\texttt{permitAll} dla m.in.\ \texttt{/api/events/**}, \texttt{/api/tracks/**}, \texttt{/api/health}) oraz publicznych tras aplikacji webowej (strona główna, katalog, detal wydarzenia, archiwum, strony prawne). Segment ten obejmuje kibiców i~pasjonatów poszukujących informacji o~terminach i~lokalizacjach, a~także osoby rozważające rejestrację.

\textbf{Kierowca} odpowiada roli systemowej \texttt{USER}. Po utworzeniu konta użytkownik utrzymuje profil, zarządza garażem pojazdów oraz składa zgłoszenia udziału w~wydarzeniach. Kluczową wartością dla tego segmentu jest możliwość dopasowania pojazdu do wymagań wydarzenia (mechanizm \texttt{carMatch} / \texttt{CategoryMatcher}) oraz śledzenie statusu zgłoszenia wraz z~powiadomieniami e-mail. W~materiałach KMR segment ten jest charakteryzowany demograficznie jako osoby w~przybliżonym przedziale 16--40~lat, geograficznie zorientowane na rynek polski. W~zaimplementowanym MVP aplikacja nie egzekwuje ograniczeń wiekowych po stronie rejestracji; kryterium pełnoletności pojawia się natomiast w~skryningu respondentów dokumentu walidacyjnego wywiadów.

\textbf{Organizator} odpowiada roli \texttt{ORGANIZER}. Segment obejmuje mniejszych i~większych organizatorów imprez (track day, drift, time attack, KJS, rajdy itd.), którzy potrzebują kanału publikacji wydarzeń oraz narzędzia do obsługi listy zgłoszeń. W~systemie uprawnienie organizatora nie jest przyznawane automatycznie przy rejestracji: użytkownik składa wniosek o~rolę, a~administrator go akceptuje lub odrzuca. Po weryfikacji organizator tworzy i~edytuje własne wydarzenia, zarządza statusami zgłoszeń oraz komunikuje się z~uczestnikami poprzez mechanizmy platformy (w~tym powiadomienia systemowe).

\textbf{Administrator} odpowiada roli \texttt{ADMIN}. Segment ten reprezentuje operatora platformy odpowiedzialnego za jakość katalogu: moderację wydarzeń oczekujących na publikację, zarządzanie rolami kont oraz rozstrzyganie wniosków o~uprawnienia organizatora. W~warstwie produktowej administrator realizuje model \emph{human-in-the-loop} przyjęty w~analizie etycznej projektu --- ostateczne decyzje moderacyjne pozostają po stronie człowieka, a~nie algorytmu.

\section{Propozycja wartości systemu}
Propozycja wartości RacePortal wynika wprost z~diagnozy problemu rozproszenia informacji o~wydarzeniach motorsportowych w~Polsce. Dotychczasowe praktyki użytkowników --- grupy w~mediach społecznościowych, witryny poszczególnych torów oraz statyczne kalendarze --- nie zapewniają jednolitego procesu odkrywania imprez, weryfikacji wymagań wobec pojazdu ani obsługi statusu zapisu. RacePortal odpowiada na ten deficyt jako \textbf{centralny katalog} oraz \textbf{warstwa operacyjna zapisów}, z~rozdzielonymi narzędziami dla poszczególnych ról.

Dla kierowców wartość koncentruje się na: (1)~przejrzystym katalogu z~widokami lista, mapa i~kalendarz oraz wspólnymi filtrami; (2)~wirtualnym garażu pojazdów; (3)~dopasowaniu pojazdu do kategorii/wymagań wydarzenia; (4)~złożeniu zgłoszenia i~otrzymywaniu powiadomień o~statusie. Dla organizatorów wartość obejmuje publikację wydarzenia, zarządzanie listą zgłoszeń, weryfikację uczestników oraz komunikację statusów bez konieczności prowadzenia procesu wyłącznie w~arkuszach i~wiadomościach prywatnych. Dla gości (kibiców i~pasjonatów) wartość sprowadza się do bezpłatnego, natychmiastowego dostępu do informacji o~terminach i~lokalizacjach, w~tym do widoku mapy oraz trasy dojazdu (domyślnie OSRM; opcjonalnie Google Maps przy skonfigurowanym kluczu API).

Wyróżnikiem produktowym względem prostych kalendarzy branżowych jest integracja łańcucha \emph{odkrycie $\rightarrow$ dopasowanie pojazdu $\rightarrow$ zgłoszenie $\rightarrow$ status}, a~nie wyłącznie publikacja dat. Założenie to potwierdza dokumentacja walidacyjna: najistotniejszym ryzykiem biznesowym jest odmowa migracji społeczności z~grup społecznościowych do scentralizowanego narzędzia; bez aktualnej podaży wydarzeń katalog traci wartość dla kierowców (problem klasycznej dwustronnej platformy).

\section{Kanały komunikacji i~dystrybucji}
Głównym kanałem dostępu do produktu jest aplikacja webowa dostępna pod adresem \url{https://raceportal.pl} (oraz wariant \texttt{www}). Interfejs webowy pełni rolę pełnego klienta transakcyjnego: rejestracja i~logowanie, garaż, zgłoszenia, panele organizatora i~administratora. Dodatkowo warstwa web została przygotowana jako PWA (manifest, service worker, nawigacja mobilna), co umożliwia instalację skrótu na ekranie początkowym urządzenia bez publikacji w~sklepach aplikacyjnych.

Kanałem uzupełniającym discovery jest aplikacja mobilna Expo, zaprojektowana świadomie jako \emph{wizytówka}: umożliwia przeglądanie katalogu i~szczegółów wydarzenia, natomiast zapis udziału realizowany jest poprzez CTA otwierające odpowiednią stronę webową. Takie rozdzielenie ogranicza zakres MVP mobilnego i~koncentruje złożoną logikę konta po stronie weba.

Kanałem komunikacji transakcyjnej jest poczta elektroniczna dostarczana przez SMTP dostawcy \textbf{Mailbux} (nadawca \texttt{noreply@raceportal.pl}). System wysyła m.in.\ wiadomości aktywacyjne i~resetu hasła, potwierdzenia zgłoszeń, zmiany statusów, powiadomienia o~anulowaniu lub zmianie wydarzenia oraz decyzje dotyczące ról i~wniosków organizatora. Wczesny wariant deweloperski oparty o~Mailpit został porzucony na rzecz realnej skrzynki domenowej, aby demonstracja rejestracji odpowiadała doświadczeniu użytkownika końcowego.

Kanałem dystrybucji kodu i~współpracy zespołu pozostaje repozytorium GitHub~\cite{raceportal:repo}. W~materiałach BMC przewidziano również promocję organiczną w~mediach społecznościowych oraz współpracę partnerską z~klubami; w~fazie MVP działania te mają charakter organizacyjny i~nie są zautomatyzowane w~kodzie aplikacji.

\section{Kluczowe zasoby i~działania}
Do zasobów kluczowych należą: pięcioosobowy zespół projektowy (specjalizacja cyberbezpieczeństwo), kod źródłowy monorepozytorium (warstwy web, API, mobile oraz pakiet wspólnych typów \texttt{packages/api-types}), relacyjna baza MySQL z~seedem danych demonstracyjnych, infrastruktura kontenerowa Docker Compose oraz środowisko produkcyjne oparte o~maszynę wirtualną i~tunel Cloudflare. Zasobem produktowym jest również katalog torów polskich wykorzystywany przy tworzeniu i~filtrowaniu wydarzeń.

Działania kluczowe obejmują: rozwój i~utrzymanie platformy; zapewnienie uruchamialności środowiska (Compose lokalnie i~na VM); moderację treści oraz weryfikację organizatorów; utrzymanie mechanizmów bezpieczeństwa (JWT, RBAC, walidacja wejścia, kierunek zgodności z~OWASP ASVS Level~1); utrzymanie dostarczalności powiadomień e-mail; a~także dokumentowanie zmian i~weryfikację testami automatycznymi. W~ujęciu BMC działania marketingowe i~budowa społeczności są uznane za konieczne dla przełamania ryzyka niskiego zainteresowania, lecz pozostają poza zautomatyzowanym zakresem oprogramowania MVP.

\section{Model działania platformy}
RacePortal funkcjonuje jako platforma dwustronna: organizatorzy dostarczają podaż wydarzeń, a~kierowcy generują popyt na starty. Administrator pełni rolę gwaranta jakości katalogu poprzez akceptację wydarzeń i~ról. Gość korzysta z~efektu sieciowego katalogu bez bariery rejestracji, co obniża koszt wejścia informacyjnego.

W~fazie MVP platforma \textbf{nie} pełni roli pośrednika płatniczego. Brak integracji z~bramką PSP (np.\ Przelewy24, Stripe) jest decyzją świadomą, potwierdzoną w~dokumentacji zakresowej i~w~kodzie. Dla wydarzeń płatnych system obsługuje statusy zgłoszenia (m.in.\ \texttt{PENDING}, \texttt{ACCEPTED}, \texttt{CONFIRMED}, \texttt{CANCELED}) oraz dołączenie dowodu wpłaty --- jako adres URL albo ścieżka pliku w~magazynie uploadów --- natomiast rozliczenie finansowe odbywa się poza platformą (np.\ przelew na dane wskazane przez organizatora). Strumienie przychodów opisane w~BMC (reklamy, płatna promocja wydarzeń, prowizje od zapisów) pozostają perspektywą rozwojową i~nie są zaimplementowane.

Model darmowego dostępu w~MVP dotyczy zarówno przeglądania katalogu, jak i~korzystania z~narzędzi kierowcy oraz panelu organizatora. Oznacza to, że weryfikacja wartości produktu na obecnym etapie opiera się na użyteczności operacyjnej, a~nie na monetyzacji.

\section{Realistyczność wdrożenia i~dalsze perspektywy}
Realistyczność wdrożenia została potwierdzona na dwóch poziomach. Poziom deweloperski obejmuje uruchomienie pełnego stosu przez Docker Compose (web, API, MySQL, kopia zapasowa) wraz z~kontami seed służącymi do demonstracji ról. Poziom produkcyjny obejmuje wdrożenie na Oracle Cloud Always Free (\texttt{VM.Standard.A1.Flex}, 2~OCPU, 12~GB RAM, region Frankfurt) z~udostępnieniem HTTPS poprzez Cloudflare Tunnel do nginx na porcie lokalnym maszyny. TLS i~DNS są po stronie Cloudflare; aplikacja pracuje w~układzie jednego originu (\texttt{/api} proxy do Spring Boot), co upraszcza konfigurację względem wcześniejszego wariantu GCP + Cloudflare Pages.

Założona w~DZW skala pilotażowa (rzędu 1--5~tys.\ użytkowników miesięcznie, profil odczytowy do ok.\ 50~RPS) jest spójna z~charakterem niskokosztowej infrastruktury dydaktycznej. Formalny test obciążenia przy 10k rekordach / 50~RPS nie został domknięty w~MVP i~pozostaje ograniczeniem odbiorczym, jawnie wskazanym w~karcie projektu.

Dalsze perspektywy --- zgodnie z~dokumentacją produktową i~materiałami BMC --- obejmują m.in.\ integrację PSP, rozbudowę powiadomień push, publikację aplikacji mobilnej w~sklepach, eksport list startowych, waitlistę/watchlistę, kalendarz iCal oraz ewentualną monetyzację poprzez oznaczone treści sponsorowane. Elementy te należy traktować jako roadmapę, a~nie jako stan bieżącej implementacji. Szczegóły architektury fizycznej przedstawiono w~rozdz.~\ref{sec:arch-fizyczna}.

\section{Kontekst prawny i~etyczny}
System przetwarza dane niezbędne do obsługi konta i~procesów biznesowych: identyfikator/nazwę użytkownika, adres e-mail, role, dane pojazdów w~garażu, zgłoszenia oraz dane wydarzeń wprowadzane przez organizatorów. Token sesji (JWT) jest przechowywany po stronie klienta. W~interfejsie udostępniono politykę prywatności (\texttt{/privacy}) oraz regulamin (\texttt{/terms}); rejestracja wymaga akceptacji obu dokumentów. Przy tworzeniu wydarzenia organizator potwierdza przetwarzanie danych zgodnie z~polityką prywatności (RODO) wyłącznie w~celu publikacji i~obsługi zgłoszeń. Kanałem kontaktowym w~sprawach ochrony danych jest adres \texttt{rodo@raceportal.pl}. Użytkownik może zamknąć własne konto w~ustawieniach (fraza potwierdzająca po stronie API).

Pełna zgodność procesowa (m.in.\ DPIA, sformalizowana polityka retencji, procedury realizacji żądań RODO w~organizacji operatorskiej) wykracza poza zakres demonstracyjnego MVP i~pozostaje obowiązkiem ewentualnego wdrożenia produkcyjnego o~większej skali.

W~warstwie etycznej dokumentacja SAI przyjmuje zasady: transparentności prezentacji wyników (brak ukrytego rankingu reklamowego w~MVP), rezygnacji z~mechanizmów uzależniających, dążenia do inkluzywności informacyjnej (wydarzenia o~różnym progu wejścia) oraz przeciwdziałania dual-use (ryzyko publikacji nielegalnych wyścigów ulicznych). Mitigacją jest weryfikacja organizatorów i~moderacja wydarzeń przez administratora. Odpowiedzialność za treść merytoryczną wydarzeń spoczywa na zweryfikowanych organizatorach w~ramach regulaminu, natomiast odpowiedzialność za poprawność mechanizmów platformy --- na zespole utrzymującym system.

\chapter{Podsumowanie}
\label{ch:podsumowanie}
\section{Największe wyzwania i sposób ich rozwiązania}
Spójność domeny zapisów i~garażu, RBAC, mapa/trasa oraz utrzymanie monorepo web+API+mobile. Po stronie infrastruktury --- uproszczenie hostingu do jednej VM z~tunelowaniem Cloudflare zamiast rozdzielonego stacku Pages/Worker.

\section{Zmiany i adaptacje w trakcie realizacji}
Przejście mobile z~parity na wizytówkę; doprecyzowanie formularzy; wspólny pakiet typów; migracja z~eksperymentów GCP/Pages na Oracle + Cloudflare Tunnel.

\section{Ograniczenia końcowej wersji systemu}
Brak PSP i~uploadu plików; mobilka bez konta; limity testów wydajnościowych i~produkcyjnego hardeningu.

\subsection{Ograniczenia wydajnościowe (RPS)}
W~wymaganiach jakościowych MVP zapisano docelowy test obciążenia: \textbf{ok.\ 10\,000 rekordów} w~katalogu oraz \textbf{ok.\ 50~RPS} przy akceptowalnym P95 odpowiedzi list/detalu. W~oddawanej wersji:
\begin{itemize}
  \item zastosowano mitigacje lokalne (paginacja listy, osobne markery mapy, indeksy / cache tam gdzie uzasadnione);
  \item \textbf{nie wykonano} formalnego load testu 10k/50~RPS (brak raportu RPS/P95 jako artefaktu odbioru);
  \item środowisko produkcyjne (Oracle Always Free + Cloudflare Tunnel) jest wystarczające do demonstracji i~ruchu prezentacyjnego, ale nie zostało zweryfikowane pod kątem założonego progu 50~RPS.
\end{itemize}
Ograniczenie to jest świadome: priorytetem było domknięcie happy-path funkcjonalnego, bezpieczeństwa podstawowego (JWT/RBAC) i~uruchamialności. Pomiar 10k/50~RPS pozostaje w~backlogu jakościowym.

\section{Możliwości dalszego rozwoju}
Płatności, upload, watchlista, iCal, waitlista, eksport list startowych, store/PWA --- por.\ \texttt{docs/pomysly-rozwoju.md}; uzupełnienie testów obciążeniowych RPS.

\section{Wnioski końcowe}
RacePortal stanowi kompletne MVP demonstracyjne katalogu i~zapisów motorsportowych z~czytelnością architektury, testami funkcjonalnymi i~ścieżką prezentacji dla odbiorcy akademickiego oraz biznesowego --- przy jasno nazwanych lukach (PSP, upload, load test RPS).
